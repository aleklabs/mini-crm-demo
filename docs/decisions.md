# Архитектурные решения и допущения

- **Supabase без отдельного backend.** React обращается к Supabase Auth, PostgREST и двум RPC. Отдельный сервер приложения не создаётся; серверные гарантии находятся в PostgreSQL.
- **RLS для разграничения доступа.** Политики строкового доступа разрешают постановщику работать со всеми активными объектами и задачами, а исполнителю — только со своими задачами и связанными объектами. Скрытие элементов интерфейса не считается мерой безопасности.
- **SQL-функции и триггеры.** `transition_task` проверяет конечный автомат, роль и назначенного исполнителя. `get_task_history` безопасно возвращает историю доступной задачи. Триггеры проверяют роль исполнителя, отделяют логическое удаление от редактирования и создают начальное событие истории.
- **Логическое удаление.** У объектов и задач заполняется `deleted_at`. Записи и история остаются в базе, но перестают быть доступны через обычные пользовательские запросы.
- **Закрытая регистрация.** Публичная и анонимная регистрация должны быть отключены отдельно в настройках облачного Supabase. Пользователей и записи `profiles` создаёт администратор.
- **Пустое описание допустимо.** `tasks.description` не принимает `NULL`, но пустая строка разрешена как осознанное отсутствие описания.
- **Нет realtime.** Данные обновляются после действий пользователя или перезагрузки страницы. Подписки и периодический опрос не реализованы.
- **Нет UI управления пользователями.** Роли, создание учётных записей и восстановление доступа остаются административными операциями Supabase.
- **Нет физического удаления из UI.** Это сохраняет аудит и связи. Административная очистка используется только изолированными автоматическими тестами для собственных фикстур.
- **Границы текущей версии.** Нет уведомлений, вложений, поиска, пагинации, аналитики и офлайн-режима. Публичное развёртывание, облачные демонстрационные данные и production-проверка требуют авторизованного доступа к отдельным проектам Supabase, GitHub и Vercel.
