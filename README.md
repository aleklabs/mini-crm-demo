# Mini CRM

Mini CRM — демонстрационное приложение строительной компании для управления объектами, задачами, назначениями и проверкой результата. Интерфейс написан на React; аутентификация, данные, разграничение доступа и бизнес-инварианты находятся в Supabase/PostgreSQL.

## Стек

- React 19, TypeScript в строгом режиме, Vite;
- React Router;
- Supabase JS, Supabase Auth, PostgREST и PostgreSQL;
- SQL-миграции и Row Level Security (RLS);
- pgTAP и Playwright;
- нативный HTML и обычный CSS;
- Vercel для статического frontend.

## Архитектура и роли

Браузер получает сессию через Supabase Auth и обращается к Data API с пользовательским JWT. В клиент попадают только URL проекта и публичный publishable key. Административные и секретные ключи frontend не использует.

Роль берётся из `public.profiles`, а не из изменяемых пользователем метаданных:

- `manager` (постановщик) видит все активные объекты и задачи, создаёт и редактирует их, назначает исполнителей, логически удаляет записи и принимает результат либо возвращает его на доработку;
- `executor` (исполнитель) видит только назначенные ему активные задачи и связанные объекты, берёт задачу в работу, отправляет на проверку и продолжает после возврата.

Публичная регистрация должна быть отключена. Авторизованный пользователь без корректной записи `profiles` не получает доступ к CRM.

## Маршруты

| Маршрут | Назначение | Доступ |
| --- | --- | --- |
| `/login` | Вход по email и паролю | Без сессии |
| `/projects` | Доступные активные объекты | Обе роли |
| `/projects/new` | Создание объекта | Manager |
| `/projects/:projectId` | Карточка объекта и задачи | Обе роли, с учётом RLS |
| `/projects/:projectId/edit` | Редактирование объекта | Manager |
| `/projects/:projectId/tasks/new` | Создание задачи | Manager |
| `/tasks/:taskId` | Карточка задачи, история и действия | Обе роли, с учётом RLS |
| `/tasks/:taskId/edit` | Редактирование задачи | Manager |
| `/my-tasks` | Все задачи текущего исполнителя | Executor |
| `/` | Перенаправление по состоянию сессии | Все |

Неизвестный маршрут показывает страницу «Страница не найдена». `vercel.json` возвращает `index.html` для прямого открытия SPA-маршрутов.

## Объекты, задачи и история

Удаление объекта или задачи является логическим: заполняется `deleted_at`, физическая строка и её история остаются в PostgreSQL. Пустое описание задачи хранится как пустая строка; `NULL` запрещён. Начальный статус и автор создания определяются базой.

Разрешённые переходы:

| Из | В | Кто выполняет | Условие |
| --- | --- | --- | --- |
| `new` | `in_progress` | Назначенный executor | — |
| `in_progress` | `in_review` | Назначенный executor | — |
| `in_review` | `accepted` | Manager | — |
| `in_review` | `rework` | Manager | Обязателен комментарий |
| `rework` | `in_progress` | Назначенный executor | — |

Создание задачи и каждый успешный переход добавляют неизменяемое событие с автором, временем, исходным и новым статусами и комментарием.

## Безопасность базы

RLS включён для всех четырёх CRM-таблиц. Политики ограничивают строки по роли, пользователю, логическому удалению и активности родительского объекта. Исполнитель не может прочитать чужую задачу или историю, создать объект, назначить себе роль либо изменить чужую задачу. Прямое изменение `tasks.status` и любые пользовательские `INSERT`, `UPDATE` или `DELETE` истории запрещены правами таблиц.

Основные SQL-функции:

- `public.transition_task(...)` — публичная `SECURITY INVOKER`-обёртка над защищённой реализацией конечного автомата;
- `public.get_task_history(...)` — возвращает историю только доступной пользователю активной задачи;
- функции схемы `private` — RLS-помощники, проверки и реализации RPC; схема `private` не выставляется через Data API.

Триггеры проверяют роль назначенного исполнителя, обеспечивают отдельную операцию логического удаления и записывают начальную историю задачи. Полный перечень схемы, политик, функций, прав и триггеров находится в `supabase\migrations`.

## Требования

- Windows 10 и `cmd.exe`;
- Node.js 24 или совместимая актуальная LTS-версия;
- npm;
- Docker Desktop с запущенным Docker Engine;
- Chromium для Playwright.

## Локальный запуск

Установите зависимости и браузер:

```cmd
cd /d C:\www\crm
npm install
npm exec playwright -- install chromium
```

Запустите локальный Supabase и проверьте состояние:

```cmd
npm exec supabase -- start
npm exec supabase -- status
```

Создайте локальное окружение:

```cmd
copy .env.example .env
```

Укажите в `.env` значения `API URL` и `Publishable key` из локального `supabase status`:

```dotenv
VITE_SUPABASE_URL=http://127.0.0.1:54321
VITE_SUPABASE_PUBLISHABLE_KEY=ваш_локальный_publishable_key
```

Запустите приложение:

```cmd
npm run dev
```

Откройте `http://127.0.0.1:5173`. Локальные постоянные пользователи не создаются: автоматические тесты создают собственные фикстуры и удаляют их после проверки.

## Миграции

Для чистого восстановления только локальной базы:

```cmd
npm exec supabase -- status
npm exec supabase -- db reset --local
```

Для отдельного облачного демонстрационного проекта сначала войдите и свяжите каталог с точно проверенным project ref:

```cmd
npm exec supabase -- login
npm exec supabase -- link --project-ref YOUR_DEMO_PROJECT_REF
npm exec supabase -- db push --dry-run
npm exec supabase -- db push
```

Не используйте `db reset` для удалённой базы. После миграций отдельно проверьте в Dashboard настройки Auth: email/password должен быть включён, публичная и анонимная регистрация — отключены, а `Site URL` и разрешённые redirect URL — соответствовать production-адресу. Локальный `supabase\config.toml` не меняет облачные настройки Auth.

## Проверки

Отдельные команды и полный последовательный прогон:

```cmd
npm run typecheck
npm run lint
npm run build
npm run test:db
npm run test:api
npm run test:e2e
npm run verify
```

`test:db` запускает транзакционные pgTAP-тесты. `test:api` проверяет Auth, PostgREST, роли, RLS, запреты и RPC с реальными пользовательскими JWT локального Supabase. `test:e2e` запускает Vite и Chromium, проверяет маршруты, интерфейс, состояния ошибок, ширину 360 px и очищает только собственные фикстуры. Эти тесты предназначены для локальной базы и не должны запускаться против облачного проекта.

## Развёртывание

1. Создайте отдельный облачный проект Supabase, примените миграции через `db push --dry-run` и `db push`, затем отдельно настройте Auth.
2. Создайте подтверждённых пользователей административно и соответствующие записи `public.profiles`. Не сохраняйте пароли или административный ключ в репозитории.
3. Импортируйте репозиторий в Vercel как Vite-проект или войдите через CLI:

```cmd
npx vercel@latest login
npx vercel@latest
npx vercel@latest --prod
```

4. В настройках Vercel добавьте только переменные сборки:

```text
VITE_SUPABASE_URL
VITE_SUPABASE_PUBLISHABLE_KEY
```

`VITE_SUPABASE_URL` должен быть облачным HTTPS-адресом, а не `127.0.0.1`. Никогда не добавляйте в Vercel или `VITE_*` ключи `service_role`, `sb_secret_*`, пароль базы, JWT secret либо токены управления. После публикации проверьте прямое открытие и reload всех маршрутов, вход обеих ролей, RLS и отсутствие ошибок запросов.
