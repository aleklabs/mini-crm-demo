# Mini CRM

Мини-CRM на React, TypeScript, Vite и Supabase. В проекте настроены локальная схема PostgreSQL, Supabase Auth, роли и RLS, конечный автомат статусов задач, интерфейс входа и просмотра доступных данных, а также управление объектами и задачами для постановщика.

## Требования

- Node.js 24 или совместимая актуальная LTS-версия
- npm
- Docker Desktop с запущенным Docker Engine

## Первый запуск в Windows cmd.exe

Установите зависимости:

```cmd
npm install
npm exec playwright -- install chromium
```

Запустите локальный Supabase (используется CLI из `devDependencies`):

```cmd
npm exec supabase -- start
npm exec supabase -- status
```

Создайте локальный файл окружения:

```cmd
copy .env.example .env
```

Возьмите `API URL` и `Publishable key` из вывода `supabase status` и укажите их в `.env`:

```dotenv
VITE_SUPABASE_URL=http://127.0.0.1:54321
VITE_SUPABASE_PUBLISHABLE_KEY=ваш_локальный_publishable_key
```

Запустите приложение:

```cmd
npm run dev
```

Откройте `http://127.0.0.1:5173`. Неавторизованный пользователь будет перенаправлен на `/login`. После входа откроется `/projects`; содержимое списка и карточек ограничивается политиками RLS локального Supabase.

Постоянные демонстрационные пользователи и данные в проект не добавляются. Браузерные тесты сами создают изолированные фикстуры через Node.js и полностью удаляют их после прогона. Для ручной проверки входа используйте существующего локального пользователя Auth, которому соответствует запись в `public.profiles` с ролью `manager` или `executor`.

## Маршруты приложения

- `/login` — вход по email и паролю;
- `/projects` — доступные текущему пользователю активные объекты;
- `/projects/new` — создание объекта, только для постановщика;
- `/projects/:projectId` — объект и доступные задачи;
- `/projects/:projectId/edit` — редактирование объекта, только для постановщика;
- `/projects/:projectId/tasks/new` — создание задачи, только для постановщика;
- `/tasks/:taskId/edit` — редактирование задачи, только для постановщика;
- `/` — перенаправление с учётом состояния сессии.

Неизвестный маршрут показывает простую страницу «Страница не найдена». Авторизованный пользователь без корректной записи `public.profiles` не получает доступ к CRM. Исполнитель при прямом открытии маршрута управления видит сообщение «Недостаточно прав» без формы объекта.

## Управление объектами

Постановщик может создать объект, изменить его название и адрес или выполнить логическое удаление. Создание и редактирование подтверждаются возвращённой через PostgREST строкой. При удалении приложение устанавливает `deleted_at`, а затем отдельным чтением проверяет, что объект больше не доступен через обычную пользовательскую выборку. Физический `DELETE` из интерфейса не выполняется; связанные задачи остаются в PostgreSQL и скрываются существующими RLS-политиками.

## Управление задачами

Постановщик может создать задачу внутри активного объекта, назначить профиль с ролью `executor`, изменить название и описание, сменить исполнителя или перенести задачу в другой активный объект. Пустое описание сохраняется как пустая строка `''`: столбец `description` запрещает `NULL`, но допускает пустое значение. `status`, `created_by`, `created_at` и начальная запись истории определяются PostgreSQL и не отправляются из React.

Удаление задачи является логическим: приложение устанавливает `deleted_at` и отдельным чтением проверяет недоступность строки для текущего пользователя. Физическая задача и её история остаются в PostgreSQL.

## Проверки

```cmd
npm run typecheck
npm run lint
npm run build
npm run test:db
npm run test:api
npm run test:e2e
npm run verify
```

`test:db` запускает транзакционные pgTAP-тесты локальной базы. `test:api` создаёт во временной локальной среде четырёх пользователей, проверяет Auth и доступ через PostgREST с их JWT, а затем удаляет тестовые данные и пользователей. `test:e2e` самостоятельно запускает Vite на порту 5173 и проверяет в Chromium вход, сессию, маршруты, RLS, состояния загрузки/ошибки/пустых данных и отображение на ширине 360 px.

Локальные ключи считываются из `supabase status` только в память Node.js-процесса и не выводятся. В окружение Vite тесты передают только публичный publishable key. `verify` последовательно выполняет все проверки в указанном выше порядке.

Публичная регистрация в локальной конфигурации отключена. Роли `manager` и `executor` берутся только из `public.profiles`; клиентские метаданные JWT не используются как источник полномочий.

## Как устроена сессия

`AuthProvider` восстанавливает сохранённую Supabase-сессию при запуске, подписывается на её изменения и отдельно загружает профиль текущего пользователя. Обработчик события Auth не выполняет запросы к базе. React Router защищает интерфейс и отвечает за навигацию, а фактический доступ к строкам PostgreSQL обеспечивают RLS-политики по JWT пользователя.

## Переходы статусов задач

Обычный пользователь изменяет статус только через RPC:

```ts
await supabase.rpc('transition_task', {
  p_task_id: taskId,
  p_new_status: newStatus,
  p_comment: comment,
})
```

Разрешены переходы `new → in_progress`, `in_progress → in_review`, `in_review → accepted`, `in_review → rework` и `rework → in_progress`. Первые, вторые и последние переходы выполняет назначенный executor; решение из `in_review` принимает manager. Для возврата в `rework` обязателен непустой комментарий. Создание задачи и каждый успешный переход автоматически добавляют запись истории.

## Восстановление локальной базы из миграций

Сначала убедитесь по выводу `status`, что используется локальный адрес `127.0.0.1`:

```cmd
npm exec supabase -- status
npm exec supabase -- db reset --local
npm run verify
```

`db reset --local` удаляет данные только локальной базы и повторно применяет миграции из `supabase\migrations`.

Для проверки Supabase и его остановки:

```cmd
npm exec supabase -- status
npm exec supabase -- stop
```

`.env` игнорируется Git. В клиенте разрешено использовать только публичный publishable key; секретный ключ Supabase добавлять в переменные `VITE_*` нельзя.
